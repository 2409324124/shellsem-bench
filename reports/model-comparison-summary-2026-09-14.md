## 题目的设计原因

| 题目 | 设计原因 | 要识别的问题 |
|---|---|---|
| Q1 | 组合 ERR、errexit、local、命令替换、子 Shell、FD、lastpipe，并比较两个变体；既要求精确输出，也要求解释 | 是否理解上下文相关的 Shell 语义；工具能否纠正输出；是否出现“运行结果抄对了，但解释仍错” |
| Q2 | 用 NUL 记录、二进制输出排除按行读取和变量捕获等捷径；叠加状态优先级、尾片段、stdin/FD 隔离；同一函数分别直接调用和放进 if 条件 | 正常路径跑通后，异常路径是否仍正确；是否吞状态、破坏字节、泄漏 FD、误等调用者后台任务；自测是否遗漏关键调用上下文 |

两题分别观察“结果与理解”和“实现与验证”，避免把工具能运行、模型自称测试通过，当作完整正确。

## n/32 如何计分

**16 个场景 × 2 种调用位置 = 32 项。** 两种调用位置是 `collect "$root"` 和 `if collect "$root"; then …; fi`，均在 Bash 5.2.37、`set -Eeuo pipefail` 环境执行。

| 场景 | 内容 / 检查目的 |
|---|---|
| empty | 没有记录 |
| one | 一条普通记录 |
| empty_record | 一个 NUL 表示一条空记录，不能当成零条 |
| hostile | 空格、换行、制表符、反斜杠、引号、通配符、前导短横线的参数保真 |
| binary | 非 ASCII 记录；worker 输出含 NUL、高位字节和末尾换行 |
| worker_failure | 多个 worker 非零，保留首个失败且继续处理 |
| scanner_failure | scanner 输出记录后以 37 退出 |
| scanner_immediate | scanner 无记录直接以 126 退出 |
| tail_only | 只有未被 NUL 终止的尾片段 |
| tail_after_record | 完整记录后还有未终止尾片段 |
| all_errors | scanner、worker、尾片段同时出错 |
| framing_over_worker | 尾片段错误 65 优先于 worker 错误 |
| worker255 | 正确保留退出码 255 |
| max_record | 8192 字节记录 |
| many | 30 条记录，检查次数和逐条处理 |
| streaming | scanner 等首个 worker 完成才继续输出，检查真正流式处理 |

每项的以下适用检查**全部通过才计 1 分，任一失败计 0 分**：

- stdout、stderr 的字节完全一致；退出码符合 `scanner 非零 > 尾片段 65 > 首个 worker 非零 > 0`。
- FD 3 报告的 count、scan、worker、framing 四字段及换行正确。
- scanner/worker 参数、worker 次数、输入隔离、不继承扫描管道、顺序执行、流式握手正确。
- 不等待调用者预先启动的后台任务；if 模式另比较调用前后的 FD 列表。

`n = 32 项中 passed=true 的数量`。例如新模型裸答 **28/32 = if 模式 16/16 + direct 模式 12/16**，四个失败均由 worker 非零时提前退出造成。旧模型 Pi 的 0/32 则是所有场景都未通过 scanner stdin 检查，部分还漏报告；**0/32 不代表每个子检查都错了**。

32 项是同一道题的相关场景，不是 32 道独立题，也不是总体成功概率。禁用 eval/外部工具、不改选项/trap、解释长度与提交格式等另行审阅，32/32 不自动等于整题合格。

## 这轮实际发现的 harness 问题

| 问题 | 证据 | 处理 |
|---|---|---|
| 上下文预算耗尽 | 新模型此前三次截断的最后请求均为 `max_tokens=1`，返回 length | 启用 Pi 历史压缩；不能把这些截断直接归因于模型能力 |
| 默认压缩保留量不适合该轨迹 | 保留最近 20000 个估算 token 时，无可压缩区段；同轨迹改为 4096 后可生成区段 | 最终配对配置使用 keepRecentTokens=4096，实际压缩事件已记录 |
| 子进程未回收 | sleep PID 1 持有 126 个僵尸，耗尽 128 PID 配额，fork 失败 | 使用 Docker --init；200 个后台任务验证后僵尸数为 0，资源限制不变 |
| 模型重复循环 | 一次新模型运行连续 12 次命令仅临时文件编号不同，输出完全相同 | 保留命令/输出证据，记为循环失败后独立重试；非按耗时截止 |

因此，之前“新模型 Pi Q2 未完整交付”的记录包含真实的运行器配置影响，不能据此断言新模型能力差。修正后新模型取得了完整提交，功能验收为 32/32。

工具访问、Pi 提示与执行循环、历史压缩、总预算同时影响结果。本实验能展示这种组合的效果，**不能给出 harness 单独提高工具调用正确率的百分比**；工具非零退出也不一定是误用，故意失败的自测同样可能非零。
