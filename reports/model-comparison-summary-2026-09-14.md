# 两道 Bash 题的新老模型对照总结

日期：2026-09-14。老模型指 `qwen3.8-max-0902`，新模型指预览代号 `qwen-latest-series-invite-2608`；“新/老”沿用本项目称呼，不根据名称中的日期推断版本先后。

## 核心结论

**有差异，最明显的是第二题裸模型首答：新模型通过 28/32 项，老模型通过 0/32 项。第一题未观察到正确性上的代际差异：裸模型都未答对，带 Pi 工具后精确输出都正确，但解释仍错。**

工具版第二题没有证据支持“新模型稳定优于老模型”或相反结论：首轮两者都没有完整交付；只有老模型追加了三次复测，因此样本不对称。老模型复测均未超时，但依然存在交付遗漏或代码错误。

目前可以说：**新模型在这道复杂 Shell 函数题的无工具首答上更接近正确；两模型在带工具条件下的完整任务可靠性都没有得到验证。** 不能据此推导整体模型排名，也不能量化 harness 的独立因果效果。

## 两道题分别测什么

| 题目 | 任务 | 判定方式 |
|---|---|---|
| Q1：执行结果与解释 | 推导两个 Bash 脚本的 stdout、stderr、退出码，解释 ERR、errexit、local、lastpipe、子 Shell 与 FD 的关系 | 两个变体逐字节结果对照；解释单独审阅 |
| Q2：修复流式处理函数 | 正确读取 scanner 的 NUL 记录、运行 worker、保持二进制输出、收集真实状态、隔离输入和描述符、处理失败优先级 | 16 个场景分别直接调用和置于 if 条件，共 32 项；源码限制与最终交付另审 |

Q1 的 2/2 仅指两个变体的精确输出正确，不代表解释合格。Q2 的 28/32 等是该题内部的功能检查数量，不是 32 道独立题的成功率。保存的中间文件另行诊断，不冒充最终答案。

## 首轮：两模型相同条件下的对照

| 条件 / 题目 | 老模型（0902） | 新模型（预览） | 可以得出的结论 |
|---|---|---|---|
| 裸模型 Q1 | 0/2；stdout 错，stderr/退出码正确 | 0/2；stdout 错，stderr/退出码正确 | 两者都未准确推导执行结果 |
| Pi Q1 | 精确输出 2/2；解释不合格 | 精确输出 2/2；解释不合格 | 工具辅助后输出改善，但理解仍不可靠 |
| 裸模型 Q2 | 0/32 | 28/32 | 本次首答中新模型明显更接近正确实现 |
| Pi Q2 | 300.0 秒上限，无最终回答 | 188.7 秒，length 截断，无完整最终回答 | 两者都未完成有效交付，失败方式不同 |
| Pi Q2 中间文件诊断 | 0/32 | 3/32 | 仅用于定位过程问题，不能当作最终提交比较 |

**Q1 的共同问题。** 工具运行使两个模型都得到了准确输出，但仍错误解释 local 状态、条件上下文对 errexit/ERR 的抑制等行为。这表明“能复述运行结果”和“能解释执行原因”需要分开评分。

**Q2 裸模型的差异。** 新模型只在直接调用且 worker 非零的四个场景失败：未保护的 worker 触发 errexit，后续状态捕获和报告不执行；if 模式全部通过。老模型错误更广，涉及 scanner 状态丢失、stdin 未隔离、误读调用者输入、worker 继承扫描 FD 等。新模型仍不是完整正确答案。

**Q2 工具版的过程问题。** 新模型中间代码使用禁止的 eval、混淆数据输出与报告 FD，并有尾片段和 wait 错误。老模型首轮中间代码留下多次 scanner 调用和不可靠的流内状态哨兵，存在 FD 清理问题。不能因为工具调用次数多，就认为验证充分。

## 老模型 Q2：追加三次复测

复测针对“原来的 300 秒超时是否必现”，使用相同模型、提示和单次预算，三个独立 Pi 会话串行运行；不向模型反馈我们的验收结果。

| 运行 | 生成耗时 | 工具调用 | 最终结果 |
|---|---:|---:|---|
| 原轮 | 300.0 秒 | 46 | 超时，无最终回答；中间代码 0/32 |
| 追加 1 | 190.5 秒 | 37 | 最终回复遗漏函数；保存代码单独诊断 26/32 |
| 追加 2 | 97.9 秒 | 19 | 提交函数，26/32 |
| 追加 3 | 205.5 秒 | 22 | 提交函数，6/32 |

三次追加均没有 API 重试，也没有重现超时。**原超时不是稳定必现现象，但错误并未随重跑消失。** 追加 1/2 仍在直接调用时错误处理 worker/wait 非零状态；追加 3 写错动态 FD 关闭语法，破坏 worker 参数和 stderr 保真。三次均自称实现正确，独立验收均不支持完整正确性。

新模型没有相应的三次 Pi Q2 复测，因此不能拿老模型的最好一次与新模型的单次结果比较，也不能比较两者稳定成功率。

另有范围纠正前额外发出的老模型裸模型记录：Q1 两次均没有完整正确 JSON 结果，Q2 两次均为 0/32。它们全部保存并披露，但未纳入首轮配对表或三次 Pi 复测统计，不能充当预先规划的对称重复实验。

## 是否可能调用错了老模型

本地核查没有发现客户端调用错误。老模型读取未跟踪的 `.env.baseline`，使用 `https://dashscope.aliyuncs.com/compatible-mode/v1`；新模型读取 `.env`，使用 `https://mdataplus-open.alibaba-inc.com/v1`。两把密钥不同，配置读取不受环境变量覆盖。

老模型的 `/models` 列表包含 `qwen3.8-max-0902`，独立最小调用返回 HTTP 200，响应模型 ID 一致；历史裸模型响应、Pi 请求体及网络端点也相符。**这能核验客户端路由，不能证明服务端实际加载的底层权重身份。** 凭据及请求鉴权头未写入仓库。

## 对 harness 的结论

本轮支持的结论是：**工具访问与 Pi 执行循环的组合，帮助模型把 Q1 的精确输出由 0/2 提升到 2/2；但没有保证解释正确，也没有保证 Q2 完整交付。**

它尚不能回答“harness 单独让工具调用正确率提高了多少”。原因是裸模型没有工具调用，不能把它的工具正确率记为零；增加 Pi 时，工具访问、多轮反馈、系统提示和总计算预算同时改变。工具错误事件也不等于所有调用的语义错误，故意失败的自测同样可能返回非零。

若后续要量化该影响，需要让新老模型都有同数量的独立重复，并在相同工具、提示和预算下比较 Pi 与最小执行循环或其他 harness。分别报告完整交付率、代码功能正确性、解释正确性和工具使用错误，不能只看是否超时或自称“全部通过”。此处是后续实验建议，本次未追加执行。

## 实验边界与留档

- 本轮关闭思考；结论仅适用于当前配置，不能代表高思考预算下的上限能力。
- 使用 Bash 5.2.37。Q1 每变体执行 50 次确认参考输出稳定；Q2 独立参考函数通过 32/32。原始参考包未提供，本项目自行构造验收数据。
- Pi 0.85.1；每题 300 秒、每回复最多 8192 token、工具调用上限 100；现有 Docker 镜像、1 CPU、512 MiB、联网，不拉镜像。
- 新模型裸 Q2 首次请求超时且无答案，失败记录保留，另一次请求取得首个答案；未覆盖或重选已取得的答案。
- 验收数据覆盖有限，源码审阅用于补充检查。例如 read 返回状态本身不能完整区分 stdin 关闭与可读 EOF；不能声称所有中途或语义错误都已被自动发现。
- 原始首答、请求体、工具事件、错误/重试、终止原因、中间代码及逐例判分均留档；最终答案、中间诊断和额外请求分别标注。
